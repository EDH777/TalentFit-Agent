# 企业人才匹配助手与人才知识库需求文档

当前版本：本地 MVP 2.3；日期：2026-10-27。

## 岗位、入库与排期边界

- 岗位分类固定为产品经理、前端开发工程师、后端开发工程师、测试工程师、AI应用开发工程师、现场实施工程师、硬件工程师、采购经理和待确认；`目标职位`已移除。已有分类优先，旧数据只按明确别名保守合并，歧义项保持待确认。
- 员工当前岗位直接读取有效主简历分类。人事可在员工页或知识库页纠正，另一处通过来源时间戳和版本校验同步，过期写入返回409。岗位分类用于筛选和展示，不替代技能证据或可投入比例。
- 简历审核接受在职员工职业履历，不要求出现求职意向；广告、文章、合同等非个人履历仍拒绝。预处理只整理审核通过的正文，格式不完整时最多基于原文重整一次，持续失败不建立索引。
- 上传每批最多3份，站内切页继续处理；刷新、关闭或退出前提醒。父段上限4000字符、子段上限2048字符，后台固定执行提取、审核、语义整理、标志分段和索引，用户不修改中间文本或分段设置。
- 项目组队使用“每日可投入比例、已安排、剩余可安排”等业务表达。公司日历默认周一至周五工作、周六周日休息；工作日员工未写个人覆盖时默认100%，请假/调休再维护覆盖，显式NULL才表示未知。100%代表一个标准工作日，未知不等于0；后台仍以0~100整数保存。演示排期带有明确演示来源，不代表真实承诺。专业 Agent 查询后形成带证据引用的结构化提案，由确定性协调节点合并；冲突不能由模型投票，无法由当前权威快照核验时必须等待补充。

## 1. 背景与目标

将原先 Dify 低代码构建的“企业人才匹配助手”和“企业人才知识库”迁移为主流框架实现的前后端分离项目，补齐账号登录、权限控制、原文件上传与人事手动维护。保留原有的人才匹配、单人画像、多人对比和普通问答四种能力，并提高数据可管理性、证据可追溯性和测试覆盖。

发布包不携带原始简历、员工台账或供应商密钥。开发环境中的资料和模型配置由使用者在本机单独提供，默认不会批量导入任何真实材料。

## 2. 角色与边界

用户要求两个身份。本次将“老板”映射为管理员，这是实施选择。

| 操作 | 人事 hr | 管理员 admin |
|---|---|---|
| 账号密码登录/退出 | 允许 | 允许 |
| 工作台查看人才数量与失败数 | 允许 | 允许 |
| 人才助手四类对话 | 允许 | 允许 |
| 当前账号历史会话 | 允许 | 允许 |
| 删除本人会话及所属消息 | 允许 | 允许 |
| 人才列表/详情读取 API | 允许 | 允许 |
| 人才维护页面 | 允许 | 不开放入口 |
| 上传、手动新增、修改、删除 | 允许 | 后端返回403 |
| 查看其他账号会话 | 禁止 | 禁止 |

一期只初始化一个人事和一个管理员账号，不开放公开注册、组织管理、在线密码重置或用户管理。后续扩展账号数不应改变现有数据和权限边界。

## 3. 页面与用户流程

登录后的主业务页面统一使用20px标题、13px说明与基础字号及small控件，工作台、人才助手、知识库和召回测试的页面标题保持一致。顶部身份栏及侧栏品牌区统一44px高，紧凑卡片和页边距。全应用统一字体、主色、边界与聚焦状态；登录页使用同一视觉体系并适配窄屏。视觉约定记录于根目录DESIGN.md，不改变现有技术栈或业务权限。

### 3.1 登录页

用户名、密码、提交按钮和可读错误。成功后进入工作台；失败统一提示“用户名或密码错误”。禁用账号不可登录。页面刷新后向服务端核验令牌与实际角色；过期/无效令牌回登录页。退出只清理本项目本地状态。

390px窗口保留左右边距，表单不得撑宽页面；长账户名在顶部省略并保留完整提示。知识库长字段在表格内部处理，不引起整页横向溢出；省略的姓名、技能与失败原因保留完整文本提示。

### 3.2 工作台

显示未删除人才总数、已入库、处理中、失败数量，并提供进入人才助手的快捷操作及示例问题。管理员和人事均可访问。

### 3.3 人才知识库（人事）

流程：上传或手动新增 → 入库结果 → 核对字段 → 检索/编辑/删除。

- 支持 PDF、DOCX、TXT、JPG、JPEG、PNG，单文件≤15MB，PDF≤20页。
- PDF按页面显示坐标还原文字顺序，处理页面旋转；过滤确认的重复水印标识，保留正常技术词和项目编号。缺失中文映射时尝试PDFium字体解码，文字不足或成片乱码时使用本地中文OCR；孤立装饰符号不能导致整份正常文字强制OCR。DOCX包含正文段落与表格。
- 文件先保存，之后提取正文、审核与抽取姓名/职位/年限/技能，再执行原入库pipeline的LLM语义整理、代码规范化、按分隔标志父子分段、关键词及向量索引。完整提取原文单独保留；入库处理文本另存，原文不被模型改写覆盖。
- 预处理按原流水线组织候选人概览、工作经历与项目经历，工作/项目逐项成子段；缺失信息省略，不补通用经历或成果。规范化补充分段边界、去除空子段和无意义缺失字段；格式不完整、主题错放、模型截断或非简历不作为成功入库。图片和扫描PDF沿用本地解析/OCR，识别后的文本进入同一整理链。
- 每批选择1~3份，选择第4份时前端拒绝，后端也在写入前返回400。显式点击“开始入库”后，逐份显示解析、字段提取、分段、关键词索引、向量索引的阶段进度和整批进度。
- 进度根据真实处理阶段更新，不是时间倒计时。每份独立提交，一份失败不阻断其余；页面关闭/断流会标记中断，已完成的记录保留。当前没有持久后台任务队列。
- 同一文件按SHA-256去重，返回409并提示已有记录；删除后允许同文件重传。
- 非简历、无效文件、模型调用失败和OCR不足时保留失败状态及原因，不生成可检索分块。人事可删除或手动补充正文。
- 手动入库由人事输入姓名、职位、年限、技能标签及简历正文；人工录入资料的正文仍可维护。上传文档仅编辑人才字段，不展示或修改提取原文；后端同样拒绝上传原文修改。
- 手动录入由人事确认有效，不强制再调用模型；上传抽取只依据原文，缺失字段不推测。
- 模型抽取的技能标签去空、去重后最多保存30项；标签较多不能导致有效简历整份入库失败，完整正文仍参与检索。字段提取异常与文件解析异常分别提示。
- 关键词BM25与Qwen text-embedding-v4向量召回通过RRF融合排序；有可检索内容时显示实际模式和嵌入模型。空库显示“暂无知识文档，入库后可查看检索状态”，没有有效分段时显示“暂无可检索内容”，不显示关键词或混合模式。首页保留文档数量与召回统计，不显示父段/子段/可检索子段/索引块数量汇总；详细数量仍在文档详情中提供。人事可以补建向量，操作时显示真实进度，平时仅提示待建立索引而不罗列块数。
- 列表显示姓名、职位、年限、标签、入库时间、状态和文档开关，各列表头居中；移除“来源”分类及数据库source_type列，保留原文件名称和原件。入库时间使用已有created_at并按北京时间显示，编辑不改变入库时间。列表采用13px字号和small控件，缩小统计、索引、上传区域及表格行高，每页10条；支持搜索、状态筛选及前端分页，最多100份文档批量启停；点击姓名进入文档详情。
- 文档详情采用紧凑父分段卡片，默认只展示第一非空行，超宽省略；下方“查看详情”在当前卡片内展开所属子分段，再次点击收起。不重复列出完整父段，也不使用子段抽屉。保留子段完整详情、分别搜索正文、筛选自身开关、分页，以及分段新增、编辑、删除和启停，父分段支持本页选择批量管理。关闭文档或父段屏蔽其下子段，重新开启不改变子段自身开关。
- 分段管理仅提供父子段增改删、启停、搜索分页及详情。修改父段会重建该父段的子段，保存前提醒覆盖其子段手工修改和开关。元数据编辑保留现有段内容/ID/开关，不从原文恢复已删段；人工录入正文变更才按确认内容重建。
- 按用户确认的Dify标准，父段上限4000字符、子段上限2048字符，新入库默认4000/2048。默认父标志`<<<RESUME_PARENT>>>`、子标志`<<<RESUME_SECTION>>>`，固定paragraph父模式。先按标志拆分，即使很短也保留独立语义；父段超长先沿完整子段边界拆，单子段超长才按换行/句子/空格再字符回退。原60字符重叠仅用于超长子段内部，不跨独立语义块重叠。父段保留子标志供编辑，只有去标志的子段进入索引。
- 文档页不提供“原始正文”“入库处理文本”“分段设置”，也不提供预览、重分段或重新预处理入口/接口。原文和中间处理文本只在后端保存；文档详情不返回这些内容或配置，公共人才详情仅返回人工录入正文，上传原文不可见。既有数据保留，不自动重跑；新上传自动执行固定处理链。
- 提供全库/单文档召回测试，输入问题及1~20条上限，展示命中子段、有效父级上下文、关键词与向量排名、RRF得分、实际模式、耗时和降级原因。与Agent共享检索实现，不生成回答、不增加正式召回次数。
- 文档/父段/子段启用状态共同约束所有检索入口与向量覆盖率。关闭或删除的内容不得从旧父段、原始正文、全文标签或姓名回退再次作为Agent证据；只有成功回答计入正式分段与父段召回次数。
- 删除需前端二次确认；后端清除分块、索引和原文件。人才记录保留删除时间，不再显示或召回。

### 3.4 人才助手

- 历史会话列表、新会话、消息发送、错误反馈和Markdown回答（支持表格）。
- 空会话仅保留一个任务引导；消息区在面板内滚动，输入区稳定在面板底部。窄屏沿用纵向会话布局，回答中的宽表格局部滚动。
- 历史列表每条会话提供删除按钮，确认后删除本人会话及全部消息；取消不删除。删除当前会话后切到剩余会话，删除最后一条后可开始新对话；删除失败保留列表与消息并允许重试，生成回答或删除等待期间禁用冲突操作。其他账号无法删除该会话。
- 用户气泡靠右、助手气泡靠左，新消息与历史消息一致，适配窄屏。
- 每条助手回复内提供可折叠的纵向执行过程，由实际节点开始/结束事件增加和更新，展示标题、类型、状态、耗时和可展开的业务摘要；节点数量、名称与顺序不在前端固定。同名节点再次执行独立记录，并行节点各自更新状态；普通问答跳过检索。成功记录随消息保存，刷新可恢复。
- 最终回答从模型流式接收，并在安全句子/换行边界脱敏后逐段显示。不展示模型思维链、原始提示词或整份简历。异常断流保留可见的部分正文、节点记录并标记未完成，不伪装为成功。
- 会话消息持久化并按账号隔离，页面刷新可恢复；最近12条历史用于理解多轮上下文。
- 查询规划器结合历史自动识别四种意图，提取用户指定人名和检索关键词。
- 人才匹配：依据岗位技能与简历证据给出推荐、匹配点、缺口和核实问题。
- 单人画像：只查询指定姓名；无法识别姓名时要求补充；没有简历时说明未找到。
- 多人对比：只比较指定人员，部分人员缺失要明确点名；不得以其他人替代。
- 普通问答：介绍助手、解释内部人才管理问题；人才事实仍须依据本次证据。
- 回复展示中文意图、时间和参考简历姓名。来源随消息保存，历史不丢失。
- 电话、邮箱、地址、证件号码等联系方式不主动输出；电话/邮箱和带标签的地址还会做规则脱敏。
- 模型不可用时返回可读503，保留已发送的用户消息，用户可稍后重发。

## 4. 质量与安全要求

前后端独立启动，通过JSON/HTTP API交互；所有业务接口要求JWT，所有写人才接口服务端校验人事角色。密码使用Argon2哈希，JWT密钥与初始密码由setup随机生成。密钥不进入前端包、日志、测试报告或版本控制。

上传物理名称使用UUID，不信任原文件名作为路径。参考材料保持原样。普通请求日志不得包含完整简历原文。模型/文件异常对网页脱敏。LLM提示明确把用户与简历正文视为数据，不执行其中的规则覆盖指令；本方案不能保证所有模型输出都绝对无误，人事应核实最终结论。

## 5. 验收标准

1. `setup.ps1` 可安装锁定依赖并生成配置；`dev.ps1` 可启动独立前后端；`stop.ps1` 可停止本项目记录的服务。
2. 两种身份登录成功，错误密码/禁用账号/无令牌被拒绝。
3. 人事能手动新增、修改、上传、删除；管理员写接口403，其他人的会话404。
4. 中文自然语言需求能召回相关岗位/技能人才，元数据修改会更新结果。
5. 非简历失败不建索引；删除清理分块/原文件且同文件可重新上传。
6. 模型真实调用完成四类意图及多轮追问，有证据来源且消息可恢复。
7. 后端回归测试、前端构建、浏览器端到端验收、依赖检查通过。

## 6. 内部项目组队

实现依据为[项目组队简化指导文档](superpowers/specs/2026-10-27-project-staffing-simplification-guide.md)。一级入口“项目组队”下设项目列表、人员准备和系统准备。人员准备维护员工档案、公司工作日和每日可投入比例；系统准备只处理上线前已有占用与初始化关闭。

默认路径为人员准备→新建组队项目→生成推荐→提交审批→管理员批准。项目表单保存即确认需求，员工范围默认为全部在职员工；项目详情使用项目需求、推荐结果、正式调配三步条，默认只显示一套当前推荐。

岗位、技能、日期和投入仍由后端确定性校验；能力证据只来自当前有效主简历子段，未知可投入比例保持未知。Agent 完整执行协调/能力/资源子图、受限 MCP、CP-SAT、独立校验和可恢复 worker；页面只隐藏内部状态，不降低 Agent 链路。高级诊断、人工替换、历史方案和运行恢复保留在折叠或高级入口。

人事可以准备数据、确认项目需求并提交推荐；管理员只能查看、关闭初始化和批准/驳回。批准事务再次核对当前来源、身份、输入指纹、工作日和可投入比例，成功后才写入正式排期。

## 项目组队默认业务路径

项目组队默认只要求人事理解四个概念：员工、能力、可投入时间、组队方案。页面按“人员准备 → 新建组队项目 → 生成推荐 → 提交审批 → 管理员批准”执行。人员准备只维护员工档案、公司工作日和每日可投入比例；上线前已有占用与初始化关闭迁移到独立“系统准备”。

项目详情使用三步条“项目需求、推荐结果、正式调配”。默认只显示当前一套推荐，隐藏需求版本、运行 ID、方案版本、求解器枚举和共享对话；能力引用与逐日排期放在折叠详情中。保存表单即确认结构化需求，员工范围默认全部在职员工，不要求用户选择必须/排除员工。

Agent仍完整执行协调 Agent、能力/资源专业子图、受限 MCP、确定性候选池、CP-SAT 和独立校验；简化只改变展示和操作入口。生成推荐、提交和审批分别由业务 facade 保护，审批事务重新检查证据、身份、工作日和可投入比例后才写入正式排期。高级诊断、人工替换、完整证据、历史方案和运行恢复继续保留，但不成为普通用户的必经步骤。

## 6. 一期之外

生产公网部署、HTTPS/网关、开放注册、用户管理、持久异步入库队列、对象存储、目录级批量导入、在线原文件预览和外部数据连接属于后续迭代。本次完善当前单一人才库及固定入库 workflow，多独立知识库和任意拖拽节点的可视化流水线编辑器未纳入。现有混合检索使用本地精确余弦扫描，尚未完成大规模语义召回或性能基准。
